# Architecture

mcp-book turns a folder of PDF books into a local, searchable index and exposes it
to an AI assistant through the Model Context Protocol. The assistant never receives
whole books: it searches, then reads only the pages or chunks it needs, and every
answer carries a citation.

## Layout

```
mcp-book/
├── pyproject.toml          # uv project, entry point `mcp-book`
├── uv.lock
├── config.toml             # library path, embedding model, chunk size
├── Dockerfile
├── docs/ARCHITECTURE.md
├── src/mcp_book/
│   ├── config.py           # config.toml loading and defaults
│   ├── models.py           # dataclasses shared by every stage
│   ├── citation.py         # "Title, Chapter, p. N"
│   ├── extract.py          # PDF → pages (text or OCR), TOC, tables, metadata
│   ├── chunking.py         # TOC-aware sections → overlapping token chunks
│   ├── embeddings.py       # embedding backends (sentence-transformers, hash, none)
│   ├── store.py            # SQLite schema: books, toc, pages, tables, chunks, FTS5, vec0
│   ├── search.py           # hybrid retrieval: BM25 + vectors, reciprocal rank fusion
│   ├── ingest.py           # orchestration, incremental by file hash
│   ├── library.py          # read API returning tool-ready dicts with citations
│   ├── server.py           # MCP tools on top of library.py (stdio, streamable HTTP)
│   └── cli.py              # `mcp-book ingest | serve | books | search`
└── tests/                  # pytest; the sample PDF is generated by a fixture
```

`library/` (PDFs) and `data/` (index) are git-ignored: the books are copyrighted
and for personal use only.

## Pipeline

```
PDF ──extract──▶ pages + TOC + tables ──chunking──▶ chunks ──embeddings──▶ vectors
                        │                              │                     │
                        └──────────────── store.py (one SQLite file) ◀───────┘
                                              │
                    search.py (FTS5 BM25 ⊕ sqlite-vec KNN, RRF) + library.py
                                              │
                                   server.py (MCP tools)
```

1. **Extract** (`extract.py`, PyMuPDF): text by page as layout blocks with
   dehyphenation. A page with fewer than `ocr_min_chars` characters is OCR'd with
   Tesseract (`ita+eng`) through PyMuPDF's `get_textpage_ocr`. The outline (TOC)
   gives chapters and sections; printed page labels are kept when the PDF has them.
   Tables come from pdfplumber, stored as rows (JSON) and as Markdown.
2. **Chunk** (`chunking.py`): the TOC splits the book into sections, refined
   inside a page when the heading text is found there. Sections are hard
   boundaries; inside a section, paragraphs (sentences when a paragraph is too
   long) are packed up to ~650 tokens (hard max 800) with ~100 tokens of overlap.
   Each chunk keeps book, chapter, section, first and last page.
3. **Embed** (`embeddings.py`): `BAAI/bge-m3` by default via sentence-transformers,
   normalised vectors. It accepts 8192 tokens, so 800-token chunks are not
   truncated (multilingual-e5 stops at 512). Token counts come from the model's
   own tokenizer when it is loaded.
4. **Store** (`store.py`): a single SQLite file. FTS5 (`unicode61
   remove_diacritics 2`) for BM25, a `vec0` virtual table (sqlite-vec, cosine,
   `book_id` partition key) for vectors. The embedding model and dimension are
   recorded; changing model requires `ingest --rebuild`.
5. **Search** (`search.py`): BM25 and KNN each return up to `candidates` hits,
   merged with reciprocal rank fusion (k = 60). Italian has no FTS5 stemmer, so
   query words of 5+ letters become prefix queries without the final vowel
   (`pomodori` → `pomodor*`): a heuristic, not a stemmer. Without embeddings the
   search degrades to BM25 only and says so.
6. **Serve** (`server.py`, official `mcp` SDK v2 `MCPServer`): stdio or
   streamable HTTP. Tools return structured dicts; each response has a
   `citation`.

## Decisions

- **One SQLite file** instead of SQLite + LanceDB: one backup unit, transactional
  re-ingestion of a book, vector filtering by book through the partition key.
- **Incremental ingest** by SHA-256: unchanged files are skipped, changed files are
  replaced atomically, `--prune` removes books whose file disappeared.
- **Pages are 1-based PDF page indexes** in every tool argument. The printed
  label (`page_label`) is returned too and used in citations when it exists, so
  the citation matches the paper book.
- **Outlines of page numbers**: scanned books often carry an outline with one flat
  entry per page titled with the printed number ("12", "xi"). When most entries
  look like that, the outline is read as page labels instead of chapters.
- **`read_pages` clamps** to 10 pages and returns `truncated` + `next_start_page`
  instead of failing, so the assistant can keep reading.
- **Book metadata** comes from the PDF; a sidecar `<file>.toml` next to the PDF
  (`title`, `author`) overrides it, since cookbook PDFs often carry junk metadata.

## Known limits

- Running headers and footers are not stripped and end up in the text.
- Multi-column layouts follow PyMuPDF's block order, which is usually but not
  always the reading order.
- Without a PDF outline there are no chapters: chunks are split by size only.
- Token counts fall back to a characters/4 estimate when no tokenizer is loaded.
